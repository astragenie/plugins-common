# DEC-002: Throw-for-infra policy everywhere; acquire() never-throws scope narrowed to contention

## Context

`result.ts`'s header already documented the intended policy: domain/expected
outcomes use `Result`, infrastructure failures (fs ENOENT/EACCES, network)
`throw` a typed `PluginError`, caught at the boundary. `jsonl.ts` and
`http.ts` (FEAT-005/SLICE-02/03) followed this from day one — every fs/network
failure in those modules throws `TransientError`.

`file-lock-manager.ts` (FEAT-001 SLICE-01 / DEC-001) diverged: it returned
`err(new TransientError(...))` for unexpected filesystem failures during
`tryAtomicWrite`, reasoning that Gate Zero required `acquire()` to "never
throw." That conflated two different outcomes under one `Result` error
channel:

1. Lock **contention** — another live process already holds the lock. This
   is an expected, routine domain outcome on the hot retry path.
2. Unexpected **filesystem failure** (EACCES, disk error, etc. — anything
   that isn't `EEXIST`) while attempting the atomic write. This is genuinely
   exceptional infrastructure failure, not a domain outcome.

Folding (2) into the same `Result` error type as (1) let a real infra fault
masquerade as a normal "try again" signal, and put `file-lock-manager.ts` at
odds with the policy every other plugin-std-consuming module in this repo
follows — a foot-gun for cross-repo adoption, where a new consumer would
reasonably assume `Result` errors are all retry-safe domain outcomes.

## Decision

We will apply throw-for-infra uniformly:

- Domain/expected outcomes (including "resource unavailable due to
  contention") → `Result`.
- Unexpected infrastructure failure → `throw` a typed `TransientError` /
  `DeterministicError`, caught at the boundary.

Concretely: `tryAtomicWrite`'s unexpected-fs branch (the non-`EEXIST` catch
arm) now `throw`s `TransientError` instead of returning
`err(TransientError)`. Its return type collapses from
`Result<boolean, TransientError>` to a plain `boolean` (`true` = wrote,
`false` = `EEXIST` contention) since the error channel is gone.

`acquire()` keeps returning `Result<{ released } | null, never>` — the `ok`
channel still distinguishes "acquired" from "not acquired" (contention), but
the error variant is now unreachable in practice (an unexpected fs failure
propagates as a thrown `TransientError` instead of an `err(...)` value).

**This refines, not discards, DEC-001.** DEC-001's real value — the hot
`acquire()`-under-contention retry path never throws — is fully preserved:
contention still returns `ok(null)`, so callers polling `acquire()` in a
retry loop see no behavior change. What changes is scope: "never throws" now
means "never throws on contention," not "never throws, period." A genuine
filesystem failure was never something a caller could sensibly retry past
without surfacing it — returning it as a quiet `Result` error made it easy to
silently swallow at a call site that only checked `result.value === null`.

`result.ts`'s header gains an explicit clause naming this split so future
modules can't re-introduce the `err(TransientError)`-for-fs pattern.

## Consequences

### Positive

- One error policy across the whole package: every fs/network module
  (`jsonl.ts`, `http.ts`, `file-lock-manager.ts`) now throws for genuine infra
  failure and only uses `Result` for expected domain outcomes.
- A real filesystem fault can no longer be silently treated as "lock busy,
  retry later" by a caller that only branches on `ok`/`value === null`.
- `result.ts`'s header now states the split explicitly, closing the gap that
  let `file-lock-manager.ts` diverge in the first place.

### Negative

- Source-breaking again on the heels of DEC-001's bump: `tryAtomicWrite`'s
  return type changes (`Result<boolean, TransientError>` → `boolean`), and
  `acquire()`'s error channel narrows to `never`. No in-repo callers exist
  outside `file-lock-manager.ts`'s own tests (repo-wide grep confirmed), so
  blast radius is bounded to this package + its test suite, same as DEC-001.
- Any caller that previously branched on `!result.ok` to retry a lock
  acquisition on fs failure must now wrap the call in try/catch instead.

### Neutral

- gepa-core minor version bump expected (mirrors the DEC-001 precedent of
  bumping rather than adding a non-throwing shim for a frozen-at-extraction
  API correction).

## Alternatives considered

- **Keep `err(TransientError)` for fs failure** (status quo) — rejected:
  perpetuates the two-tier confusion (contention vs. genuine fault) under one
  `Result` error channel and diverges from the rest of the package's policy
  right before cross-repo adoption.
- **Make `acquire()` truly never-throw for ALL failures** (wrap the throw
  back into `err(...)`) — rejected: this is what DEC-001 originally did and
  is the exact pattern this decision supersedes/refines; it under-serves
  callers who need to distinguish "try again" from "something is actually
  broken."
