## Lessons

- The correctness reviewer's empirical probing (running real execFile against this machine) caught a HIGH the builder's green suite missed: `maxBuffer` overflow (Node default 1MB, trips on verbose `git log`/`diff`) was misclassified as a spawn failure and thrown as a WRONG-category `TransientError`. The initial two-way (exit-code vs spawn-failure) discrimination was too coarse — child_process has a THIRD failure mode (ran-but-output-too-big) that is deterministic, not transient.
- Error-category correctness matters as much as pass/fail: a retryable-vs-deterministic misclassification on a frozen API would mislead every downstream consumer's retry logic. Fixed to `DeterministicError`/`E_GIT_MAXBUFFER` before freeze.
- Timeout tests need a deterministic race: the builder's first timeout test used `git --version` (too fast, racy) — switched to `git hash-object --stdin` (blocks on stdin EOF that never comes) so a 1ms timeout reliably wins. "Assert it settles" is not a real assertion; assert the concrete outcome (`ok:false`/`status:-1` via SIGTERM).

## What went wrong

## What I would do differently next time

For any wrapper over child_process/exec, require the builder to enumerate ALL error-category branches (exit-code, maxBuffer, timeout/signal, spawn-error) with a test each, before returning — not just success + one failure.
