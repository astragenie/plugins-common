## Lessons

- A pre-work architect ADR earns its keep when it is CONSUMED: this ADR's five decisions (push-not-pull, producer-semver versioning, semver.lt staleness comparator, per-producer file-pair layout, throw-DeterministicError failures) were each directly implemented by SLICE-1 and SLICE-3 without rework — the design held under build. That's the signal a pre-flight ADR was worth the 3 points.
- The architect corrected a false premise in the FEAT itself: the stated precedent (@astragenie/astramem-client) is a hand-written published client, NOT a generated manifest — only pinned-artifact-consumption transfers. Catching that before build stopped SLICE-1 from copying an inapplicable pattern.

## Surprises

- The staleness comparator choice (semver vs generatedAt timestamp) mattered more than expected: timestamps across independently-scheduled CI in different repos are corrupted by clock skew, so generatedAt was demoted to observability-only and semver became the sole comparator — a decision that directly shaped SLICE-3's reader.

## Followups

- See FEAT-012: the ADR's broader reader description (multi-producer merge + collision detection) was not fully realized in SLICE-3 (AC-3 only). Tracked for a follow-on slice.

## Decisions

Design of record captured in the ADR artifact; no loop DEC minted (the ADR is forward-looking design, not a retrospective decision record).

## What went well

Design is concrete, buildable, and justified per-question with rejected alternatives. Both downstream code slices built from it cleanly.

## What went wrong

The ADR committed SLICE-3 to multi-producer merge/collision which SLICE-3 did not fully deliver — the design was broader than the executed AC-3. Not an ADR defect, but the plan didn't reconcile the two.

## What I would do differently next time

Split an ADR that spans multiple code slices into per-slice AC checklists so a downstream slice can't silently under-deliver against it.
