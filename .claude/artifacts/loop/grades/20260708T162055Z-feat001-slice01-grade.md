## Lessons

- gepa-core lives INSIDE the plugins-common monorepo, so Gate Zero + plugin-std extraction are in-repo; consumer migrations for runner-plugin / dev-team / astramem-plugin are cross-repo and need companion FEATs in those backlogs.
- The runner loop CLI statically imports `@astragenie/astramem-client` in `memory-context.mts`, so `memory.enabled=never` does NOT bypass it — the package had to be present in the runner plugin cache `node_modules` or every loop command ENOENTs at slice-start.
- plugin-std needed a `tsconfig.build.json` to emit `dist/*.d.ts` before workspace consumers (gepa-core) could typecheck against it.
- `PluginError` uses `instanceof` for `isPluginError`/`isTransient` — fragile if plugin-std is ever dual-bundled; fine under workspace symlink today.

## Decisions

### DEC-001: Never-throws contract via Result return, source-breaking signature bump

**Rationale**: gepa-core `TrialStore.put()` and `LockManager.acquire()` changed from throwing to returning `Result<T, PluginError>`. Source-breaking, but a repo-wide grep confirmed no in-repo callers outside the package's own tests. Bumped gepa-core 0.7.0→0.8.0 with a CHANGELOG entry rather than adding a non-throwing shim.

**Consequences**:
- Callers now get typed, discriminated errors (`E_TRIAL_SCHEMA` deterministic, `E_LOCK_WRITE` transient) instead of unhandled exceptions.
- First-consumer proof that `@astragenie/plugin-std` error taxonomy works before other repos adopt it.
- Any future external consumer of gepa-core 0.7.x must update call sites on upgrade.
